# Project Guidance

## User Preferences

- Deliberately narrow tenancy builds: change only the named layer, never refactor unrelated endpoints in the same session
- Do not change current Norwood behavior for familyId = "norwood"
- Preserve the protected baseline: Tenancy 1A family model and migration, existing claims, Steward records, Archive, Research, Board, Messaging, Recipes, Stories, notifications, Security Pass 1 and Pass 2 behavior
- The family-scoped helpers must be the canonical source of truth; never leave two independent authorization implementations
- Temporary compatibility wrappers must be clearly marked as temporary
- Never expose family IDs or principals in user-facing errors
- Never use the Caffeine admin role for Steward authority
- No OAuth or Internet Identity browser testing; report authenticated browser checks as manual tests

## Verified Commands

- **typecheck**: `pnpm typecheck`
- **fix**: `pnpm fix`
- **build**: `pnpm build`

## Learnings

- Tenancy 1C-D2-B family-scoped the four Recipe mutation hooks in src/frontend/src/hooks/useRecipes.ts: useSubmitRecipe/useApproveRecipe/useRejectRecipe/usePublishRecipe fork on useFamilyScopedId() exactly like useBoard.ts/useMessaging.ts — undefined keeps the legacy no-familyId call, else the *ForFamily method with familyScopedId as the FIRST argument; hook signatures are unchanged so RecipeContributePage and AdminApprovalPage needed no edits.
- React Query invalidateQueries matches by key PREFIX, so a bare ['recipes','pending'] filter also matches ['recipes','pending',<otherFamily>]. Family-separated invalidation needs the bare queryKey PLUS a predicate (query) => query.queryKey[2] === familyScopedId; the shared recipeListInvalidation(kind, familyScopedId) helper in useRecipes.ts does this — default family keeps the exact legacy bare-prefix filter, non-default adds the predicate.
- The Recipe mutation family-separation cover is src/frontend/src/RecipesMutationFamilyScopedCallShape.cover.test.tsx (non-default branch: *ForFamily call shapes, no hard-coded norwood, family-separated invalidation) plus RecipesMutationFallbackCharacterize.test.tsx (no-provider legacy fallback and actor-not-ready guard).
- usePublishRecipe is family-wired but has no page consumer; the 'if used' criterion is satisfied at the hook level.
- The local-deploy autonomous tester cannot reach the authenticated Recipe surfaces: the browse screen renders but Add Recipe shows a 'Sign in to add a recipe' gate and /steward/approvals falls back to the public home page, so the preflight reports inconclusive with auth and those runtime checks remain manual tests.
- Tenancy 1C-D3-A family-scoped the Family Stories backend: the canonical endpoints are the 9 *ForFamily methods in mixins/family-history-scope-api.mo with pure domain logic in lib/family-history-scope.mo; the legacy no-familyId Story endpoints are TEMPORARY wrappers in that same mixin delegating with FamilyTypes.DEFAULT_FAMILY_ID.
- lib/family-history.mo and mixins/family-history-api.mo were superseded and emptied to inert stubs (module {}; / mixin () {};) with their imports/includes removed from main.mo, so exactly one implementation of every Story read, mutation, and authorization check exists; Mystery logic was extracted verbatim to lib/mystery.mo and mixins/mystery-api.mo.
- Story family boundary is enforced by belongsToFamily(story, familyId) in lib/family-history-scope.mo; a foreign-family storyId returns the existing safe not-found result (?null / []), never a distinguishable error that leaks family existence.
- The migration 20260926_000000.mo adds familyId to stories using the subset OldActor/NewActor form and backfills DEFAULT_FAMILY_ID; the OQL story entity in main.mo needed familyId added to both .sample and .payload.
- countPendingForFamily's story loop must filter on s.familyId == familyId and s.status == #Pending; the archive-family-isolation.behavior.test.ts assertion that stories stay family-agnostic was stale and had to be updated for D3-A.
- Stories have no single originating person (unlike Recipes), so the existence guard is a per-related-member profile check (requireStoryPeopleExistInFamily) placed AFTER requirePeopleInFamily to preserve the family-boundary denial message for foreign-family references.
- The PocketIC lane's staleness gate compares src/backend/dist/backend.wasm mtime against the newest src/backend/**/*.mo mtime; after adding new Motoko files you must run mops build to refresh the wasm or the lane skips with stale_backend_wasm and runs zero backend tests.
- The local-deploy autonomous tester cannot reach the family-scoped Story UI: the Family Stories screen renders but listApprovedStories/listPendingStories are rejected with IC0503 'Unauthorized: You must be signed in', and the sign-in modal offers only Google/Apple OAuth, so the preflight reports inconclusive with auth and those runtime checks remain manual tests.
- Tenancy 1C-D3-B family-scoped the Story frontend read hooks in src/frontend/src/hooks/useFamilyHistory.ts: useApprovedStories/usePendingStories fork on useFamilyScopedId() exactly like useRecipes.ts/useBoard.ts (undefined keeps the legacy no-arg call and legacy key; else the *ForFamily method with familyScopedId appended to the query key).
- The generated Story bindings expose no legacy unscoped getStory — only getStoryForFamily(familyId, storyId) — so the new useStory detail hook always passes the active family id explicitly (default family included) and puts familyId in the cache key; this is required, not a hard-code violation.
- StoriesPage's detail view now reads through useStory (family-scoped) rather than resolving from the already-fetched approved list, so a non-default family never resolves another family's story; browse/pending lists, filters, sorting, and empty states are unchanged.
- Story mutation invalidation keeps bare prefix keys (['familyHistory','stories','pending']); React Query prefix matching still matches family-appended keys, so non-default family caches refresh without any mutation change — mutation family wiring remains deferred to D3-C.
- Per-person Story filtering is client-side over the family-scoped approved list (StoryFilterBar matches story.relatedMemberIds); no per-person Story read hook or family-scoped per-person Story endpoint exists, so that requirement is satisfied vacuously and the hook is excluded by doNotBuild.
- The Story family-wiring cover is src/frontend/src/StoryReadsFamilyScopedCallShape.cover.test.tsx (9 tests: *ForFamily call shapes with familyId first, family-appended query keys separating Family A from Family B, no literal default family id on the non-default branch, and a StoriesPage browse+detail journey) plus the existing FamilyHistoryStoryReadsCharacterize.test.tsx default-family baseline.
- The local-deploy autonomous tester cannot reach the family-scoped Story UI: the Family Stories screen renders its heading and description but listApprovedStories/listPendingStories/getStoryForFamily are rejected with IC0503 'Unauthorized: You must be signed in', and the sign-in screen offers only Google/Apple OAuth, so the preflight reports inconclusive with auth and those runtime checks remain manual tests.
- Tenancy 1C-D3-C family-scoped the five Story mutation hooks in src/frontend/src/hooks/useFamilyHistory.ts: useSubmitStory/useApproveStory/useRejectStory/useAddCanonicalStory/useUpdateCanonicalStory fork on useFamilyScopedId() exactly like useRecipes.ts — undefined keeps the legacy no-familyId call, else the *ForFamily method with familyScopedId as the FIRST argument; hook signatures are unchanged so StoriesPage.tsx and StoryContributionForm.tsx needed no edits.
- The Story detail cache key is ['familyHistory','stories','detail',id,familyId] (familyId at index 4) while pending/approved keys put familyId at index 3, so the shared storyInvalidation(kind, familyScopedId) helper in useFamilyHistory.ts selects the predicate index by kind (4 for 'detail', 3 otherwise); the default family keeps the exact legacy bare-prefix filter.
- Story mutation invalidation now covers the approved list, the pending list, and the Story detail key; useSubmitStory invalidates pending, useApproveStory invalidates pending+approved+detail, useRejectStory invalidates pending+detail, and useAddCanonicalStory/useUpdateCanonicalStory invalidate approved (+detail for update).
- The Story mutation family-wiring cover is src/frontend/src/StoryMutationFamilyScopedCallShape.cover.test.tsx (16 tests: *ForFamily call shapes with familyId first, no literal default family id, family-separated invalidation predicate, Family A vs Family B cache separation) plus the default-family baselines FamilyHistoryStoryReadsCharacterize.test.tsx and FamilyHistoryStoryMutationFallbackCharacterize.test.tsx.
- The local-deploy autonomous tester cannot reach the family-scoped Story UI: the Family Stories screen renders its heading and subtitle with empty card placeholders but listApprovedStories/listPendingStories/getStoryForFamily are rejected with IC0503 'Unauthorized: You must be signed in', and the sign-in screen offers only Google/Apple OAuth, so the preflight reports inconclusive with auth and those runtime checks remain manual tests.
