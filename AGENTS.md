# Project Guidance

## User Preferences

- Deliberately narrow tenancy builds: change only the named layer, never refactor unrelated endpoints in the same session
- Do not change current Norwood behavior for familyId = "norwood"
- Preserve the protected baseline: Tenancy 1A family model and migration, existing claims, Steward records, Archive, Research, Board, Messaging, Recipes, Stories, notifications, Security Pass 1 and Pass 2 behavior
- The family-scoped helpers must be the canonical source of truth; never leave two independent authorization implementations
- Temporary compatibility wrappers must be clearly marked as temporary
- Never expose family IDs or principals in user-facing errors
- Never use the Caffeine admin role for Steward authority
- No OAuth or Internet Identity browser testing; report authenticated browser checks as manual tests

## Verified Commands

- **typecheck**: `pnpm typecheck`
- **fix**: `pnpm fix`
- **build**: `pnpm build`

## Learnings

- The Story detail cache key is ['familyHistory','stories','detail',id,familyId] (familyId at index 4) while pending/approved keys put familyId at index 3, so the shared storyInvalidation(kind, familyScopedId) helper in useFamilyHistory.ts selects the predicate index by kind (4 for 'detail', 3 otherwise); the default family keeps the exact legacy bare-prefix filter.
- Story mutation invalidation now covers the approved list, the pending list, and the Story detail key; useSubmitStory invalidates pending, useApproveStory invalidates pending+approved+detail, useRejectStory invalidates pending+detail, and useAddCanonicalStory/useUpdateCanonicalStory invalidate approved (+detail for update).
- The Story mutation family-wiring cover is src/frontend/src/StoryMutationFamilyScopedCallShape.cover.test.tsx (16 tests: *ForFamily call shapes with familyId first, no literal default family id, family-separated invalidation predicate, Family A vs Family B cache separation) plus the default-family baselines FamilyHistoryStoryReadsCharacterize.test.tsx and FamilyHistoryStoryMutationFallbackCharacterize.test.tsx.
- The local-deploy autonomous tester cannot reach the family-scoped Story UI: the Family Stories screen renders its heading and subtitle with empty card placeholders but listApprovedStories/listPendingStories/getStoryForFamily are rejected with IC0503 'Unauthorized: You must be signed in', and the sign-in screen offers only Google/Apple OAuth, so the preflight reports inconclusive with auth and those runtime checks remain manual tests.
- Tenancy 1C-D4-A family-scoped the Family Mystery backend: canonical endpoints are the 9 *ForFamily methods in mixins/mystery-scope-api.mo with pure domain logic in lib/mystery-scope.mo; legacy no-familyId Mystery endpoints are TEMPORARY wrappers in that same mixin delegating with FamilyTypes.DEFAULT_FAMILY_ID.
- lib/mystery.mo and mixins/mystery-api.mo were emptied to inert stubs (module {}; / mixin () {};) with their imports/includes removed from main.mo, so exactly one implementation of every Mystery read, mutation, and authorization check exists.
- Mystery family boundary is enforced by belongsToFamily(mystery, familyId) and contributionBelongsToFamily(contribution, familyId) in lib/mystery-scope.mo; a foreign-family mysteryId/contributionId returns the existing safe not-found result (?null / []), never a distinguishable error that leaks family existence.
- The legacy listMysteries and listTimelineEvents were ungated public queries, so their TEMPORARY wrappers stay ungated (delegating to the canonical lib with DEFAULT_FAMILY_ID) to preserve the protected Norwood baseline; only the new canonical *ForFamily reads gate on requireApprovedFamilyMemberForFamily.
- submitMysteryContributionForFamily enforces the target mystery belongs to familyId via MysteryScopeLib.getForFamily and traps 'Mystery not found' for a foreign-family mysteryId, so a Family A member cannot contribute to a Family B mystery.
- The migration 20260927_000000.mo adds familyId to mysteries and mysteryContributions using the subset OldActor/NewActor form and backfills DEFAULT_FAMILY_ID; the OQL mystery entity was switched to MysteryRow via MysteryScopeLib.mysteryRows and both mystery/mysteryContribution entities needed familyId added to .sample and .payload.
- lib/pending-count.mo countPendingForFamily now filters mystery contributions on m.familyId == familyId, so Family A pending contributions never inflate Family B's Pending Contributions badge.
- Mysteries have no single originating person, so the existence guard is a per-related-member profile check (requireMysteryPeopleExistInFamily) placed AFTER requirePeopleInFamily to preserve the family-boundary denial message for foreign-family references.
- The Mystery family-scoping cover is test/pocketic/mystery-family-scope.cover.test.ts (15 tests) plus test/pocketic/mystery-default-family.characterize.test.ts (15 tests, default-family baseline) and test/pocketic/mystery-family-scope.upgrade.test.ts (real previous-revision upgrade backfilling familyId='norwood' idempotently).
- The local-deploy autonomous tester cannot positively demonstrate the Mystery listing/detail flow: the Family Mysteries screen renders its heading and filter tabs with a clean 'No mysteries yet' empty state, but no mystery records exist for the default family and creating one requires sign-in, which the dispatch excludes from browser testing, so the preflight reports inconclusive with test_data and those runtime checks remain manual tests.
- Tenancy 1C-D4-B family-scoped the Mystery frontend READ hooks in src/frontend/src/hooks/useFamilyHistory.ts: useMysteries/usePendingMysteryContributions/useTimelineEvents fork on useFamilyScopedId() exactly like useRecipes.ts (undefined keeps the legacy no-arg call and legacy key; else the *ForFamily method with familyScopedId appended to the query key).
- The generated Mystery bindings expose no legacy unscoped getMystery or listMysteryContributions — only getMysteryForFamily(familyId, mysteryId) and listMysteryContributionsForFamily(familyId, mysteryId) — so the new useMystery and useMysteryContributions hooks always pass the active family id explicitly (default family included) and put familyId in the cache key; this is required, not a hard-code violation.
- MysteriesPage's detail view now reads through useMystery (family-scoped) rather than resolving from the already-fetched list, so a non-default family never resolves another family's mystery; browse/filter/empty states are unchanged. MysteriesPage probes useMystery(0n) on mount (selectedId ?? 0n), issuing a getMysteryForFamily(familyId, 0n) call that returns null.
- The Mystery read family-wiring cover is src/frontend/src/MysteryReadsFamilyScopedCallShape.cover.test.tsx (11 tests: *ForFamily call shapes with familyId first, family-appended query keys separating Family A from Family B, no literal default family id on the non-default branch, and a MysteriesPage browse+detail journey) plus the default-family baseline src/frontend/src/FamilyHistoryMysteryReadsCharacterize.test.tsx (18 tests).
- FamilyHistoryCover.test.tsx's default-family Mystery detail journey needed a getMysteryForFamily mock added because the detail view now reads through the family-scoped detail endpoint instead of resolving from the list.
- The local-deploy autonomous tester could not verify runtime behavior for the Mystery read wiring: the PocketIC sidecar health check failed at http://127.0.0.1:8100/healthz (HTTP 503), so the preflight reported inconclusive with local_deploy_failed and the authenticated Mystery screen checks remain manual tests.
- Tenancy 1C-D4-C family-scoped the five Mystery MUTATION hooks in src/frontend/src/hooks/useFamilyHistory.ts: useSubmitMysteryContribution/useReviewMysteryContribution/useCreateCanonicalMystery/useUpdateCanonicalMystery/useMarkMysteryResolved fork on useFamilyScopedId() exactly like the Story mutation hooks — undefined keeps the legacy no-familyId call, else the *ForFamily method with familyScopedId as the FIRST argument; hook signatures are unchanged so MysteriesPage.tsx, MysteryDetail.tsx, and MysteryContributionForm.tsx needed no edits.
- The Mystery cache family-id slot differs by key: list ['familyHistory','mysteries',familyId] and timeline ['familyHistory','timeline',familyId] put it at index 2, while detail ['familyHistory','mysteries','detail',id,familyId], contributions ['familyHistory','mysteries','contributions',mysteryId,familyId], and pending ['familyHistory','mysteries','contributions','pending',familyId] put it at index 4 — so mysteryInvalidation(kind, familyScopedId) selects the predicate index by kind (2 for 'list'/'timeline', 4 otherwise) and the default family keeps the exact legacy bare-prefix filter.
- Mystery mutation invalidation coverage is preserved exactly: useSubmitMysteryContribution invalidates pending contributions + pendingContributionsCount; useReviewMysteryContribution invalidates pending contributions + Mystery list + pendingContributionsCount + notifications; useCreateCanonicalMystery/useUpdateCanonicalMystery/useMarkMysteryResolved invalidate the Mystery list only — each now family-separated via mysteryInvalidation.
- The Mystery mutation family-wiring cover is src/frontend/src/MysteryMutationFamilyScopedCallShape.cover.test.tsx (19 tests: *ForFamily call shapes with familyId first, no literal default family id, family-separated invalidation predicate, Family A vs Family B cache separation) plus the default-family baselines FamilyHistoryMysteryReadsCharacterize.test.tsx (18 tests) and FamilyHistoryMysteryMutationFallbackCharacterize.test.tsx (6 tests).
- The local-deploy autonomous tester verified the Family Mysteries page renders its heading, five status filters, and empty state without a blank screen (filter interaction updates the empty state to 'No open mysteries'); authenticated Mystery mutation flows remain manual tests because the sign-in screen offers only Google/Apple OAuth.
