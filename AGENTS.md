# Project Guidance

## User Preferences

- Frontend-only phases: change only the named layer, never refactor unrelated endpoints or domains in the same session
- Use the existing centralized active familyId (useFamilyScopedId); never hard-code 'norwood'
- Preserve the protected tenancy/security baseline and current Norwood behavior
- No OAuth or Internet Identity browser testing; report authenticated browser checks as manual tests
- Keep Account, PersonProfile, FamilyMembership, and StewardRecord as separate concepts; ProfileClaim is retained for compatibility
- StewardRecord is the single source of Steward authority; onboarding state is progress tracking only, never a second authorization system
- FamilyInvitation is a secure onboarding transport record, separate from PersonProfile, ProfileClaim, FamilyMembership, StewardRecord, and FoundingStewardNomination; acceptance does not by itself grant unrestricted family access
- Invitation preview must never expose sensitive relationship context (adopted, foster, step, biological, guardian) as public invite labels
- Invitation tokens are opaque and URL-safe; only the stored digest is used for validation, and raw tokens are never stored permanently
- MembershipConfirmation is a separate record from FamilyMembership, ProfileClaim, StewardRecord, and FamilyInvitation; confirmation state tracks resolution without duplicating FamilyMembership.status
- Confirmation APIs expose only simple relationship labels (Parent/Child, Sibling, SpousePartner) and never sensitive relationship context
- Applicant-facing confirmation reads must be redacted: never expose confirmer account principals, sensitive relationship context, private notes, or unrelated profile information
- Confirmation UI must use neutral, family-safe wording with no accusatory language (no fraud/fake/imposter)
- Confirmation request surfaces are family-scoped: a Family A request never renders while Family B is active, and cache invalidation is family-exact, never a bare cross-family prefix
- A user whose membership is still Pending must not receive normal family navigation; the applicant status card works within the existing limited onboarding state
- Preserve the existing Norwood visual language (typography, beige/off-white surfaces, rounded cards/buttons, spacing); do not redesign
- User-visible family names come from the active Family record's displayName, never derived from familyId; the technical familyId suffix is never shown
